# AI PM 經理人班 — 全課名詞對照表

**用途**：本課程所有專有名詞的中英對照、一句話白話解釋、以及首次出現的週次。
**規則**：每個名詞在教材中第一次出現時都必須有一句話定義（見 `課程邊界與驗證規範.md` 邊界 A 硬性規則 1）。本表是那些定義的統一出處——**教材裡的定義與本表不一致時，以本表為準。**
**版本**：v1.0（2026-10-02｜對應 P0-5 修正）
**維護**：每開發一週教材時，把該週「本週新名詞」欄位的內容合併進本表。

---

## 怎麼用這份表

- **學員**：讀到不懂的詞先查這裡。每一條都寫到「它在會議上代表什麼決策」為止，不寫技術原理。
- **教材開發者**：寫新一週教材時，先查本表有沒有這個詞。有 → 沿用同一句定義；沒有 → 新增一列，並放進該週的「本週新名詞」欄位（每週上限 8 個）。

## 一、AI 技術相關名詞

| 中文 | 英文 | 一句話白話解釋 | 它代表什麼決策 | 首次出現 |
|---|---|---|---|---|
| 人工智慧 | Artificial Intelligence, AI | 「讓機器做出看起來需要智慧的事」的總稱 | 聽到這個詞先追問是哪一層——不是所有 AI 都是機器學習 | W01 |
| 規則式系統 | Rule-based system | 人把判斷邏輯一條一條寫死的系統 | 規則穩定的場景裡它是**更好**的答案：便宜、快、每個決定都解釋得出來 | W02 |
| 機器學習 | Machine Learning, ML | 不靠人寫規則，而是讓電腦從大量例子裡自己找出規律 | 需要有歷史資料才做得起來 | W02 |
| 深度學習 | Deep Learning, DL | 機器學習的一種做法，擅長處理圖片、聲音、文字 | 資料量需求更大、更貴、更難解釋 | W02 |
| 大型語言模型 | Large Language Model, LLM | 吃進巨量文字訓練出來的模型，能力是「根據前面的文字猜出接下來的文字」 | 它會講錯，而且每次使用都要付費 | W02 |
| 判別式 AI | Discriminative AI | 做判斷題的 AI：回答「這是哪一類」或「這個數字是多少」 | 驗收可以量化；需要大量有標註的歷史資料 | W02 |
| 生成式 AI | Generative AI | 做作文題的 AI：產生一段原本不存在的內容 | 驗收需要人來評，**這件事常常沒被排進時程** | W02 |
| 訓練 | Training | 用資料把模型做出來的過程 | 一次性、昂貴、做完才知道效果 | W02 |
| 推論 | Inference | 模型做好之後，每一次拿它來回答問題的過程 | 每次都有成本；使用者要等多久是設計問題 | W02 |
| 標註 | Labeling / Annotation | 人工在資料上貼標籤，告訴模型什麼是正確答案 | 判別式專案最大的隱藏人力成本 | W02 |
| Token（詞元） | Token | 模型處理文字的最小單位，也是計價單位（中文約一字 1–2 個） | **成本**。功能怎麼設計直接決定營運成本的量級 | W02 |
| 脈絡長度 | Context window | 模型一次能讀進去的最大份量 | **功能邊界**。超過了前面的內容會被擠掉，而且使用者不會收到警告 | W02 |
| 幻覺 | Hallucination | 模型講出聽起來合理、語氣肯定，但其實不正確的內容 | 它不是 bug，修不掉。對策是設計一個預設它會錯的流程 | W02 |
| 微調 | Fine-tuning | 用自己的資料把通用模型再訓練一次，改變它的行為 | 適合「**怎麼說**」：風格、格式、語氣、分類方式 | W02 |
| 檢索增強 | RAG, Retrieval-Augmented Generation | 不動模型，但回答前先去你的資料庫撈出相關資料給它看 | 適合「**說什麼**」：會變動的事實。代價是你的文件有多亂它就有多亂 | W02 |
| 資料飛輪 | Data flywheel | 使用 → 產生資料 → 改善模型 → 體驗變好 → 更多使用的循環 | 它**不會自動發生**，要問「蒐集什麼訊號、誰回灌、多久一次」 | W02 |
| 冷啟動 | Cold start | 新商品沒人點過、新使用者沒有行為紀錄，系統對他們一無所知 | 這是產品設計問題，不是技術會自己解決的事 | W02 |
| 模型效果衰退 | Model drift / decay | 環境變了，模型過去學到的規律不再成立 | 驗收條件要有「定期重新檢視」的機制與負責人 | W02 |
| 基準線 | Baseline | 「不用 AI 的話，現況是什麼水準」 | 沒有基準線，任何準確率數字都沒有意義 | W01 |
| 人在迴路 | Human-in-the-loop, HITL | 在流程的某個環節安排人工確認 | 重點是那個人**看得到足夠資訊去判斷**，只有同意／退回按鈕等於沒有複核 | W02 |

## 二、產品管理相關名詞

| 中文 | 英文 | 一句話白話解釋 | 它代表什麼決策 | 首次出現 |
|---|---|---|---|---|
| 產品需求文件 | PRD, Product Requirements Document | 一份說清楚「要做什麼、為誰做、做到什麼程度算完成」的文件 | 它是團隊對「完成」的共同定義，不是給老闆看的報告 | W01（完整教學於 W06） |
| 需求定義 | Requirement definition | 把模糊的想法轉成明確、可驗證的描述 | 這跟「會提問」是同一件能力 | W01 |
| 優先級排序 | Prioritization | 決定哪些做、哪些不做、哪些先做 | 取捨的本質是承擔責任，這件事必須有人說出口 | W01 |
| 人物誌 | Persona | 用一個虛構但具體的人，代表一群真實使用者的典型樣貌 | 它的用途是讓團隊討論時有共同對象，不是行銷素材 | W05 |
| 使用者旅程 | User journey | 使用者從遇到問題到解決問題，整段過程的步驟與感受 | 用來找出「哪一步最痛」，決定先改哪裡 | W05 |
| 使用者故事 | User story | 用「作為某某，我想要某某，以便某某」寫成的一句需求 | 它強迫你寫出「為了什麼」，避免只列功能 | W06 |
| 驗收條件 | Acceptance criteria | 一條一條寫清楚「做到什麼程度才算完成」 | 生成式 AI 的驗收條件必須回答「誰來評、用什麼標準」 | W06 |
| 邊界案例 | Edge case | 不常發生、但一發生就會出事的極端情況 | AI 寫規格最常漏掉的就是這一塊 | W06 |
| 非功能性需求 | Non-functional requirements | 不是「做什麼」而是「做得多好」：速度、穩定度、安全性 | 常被漏掉，但它決定使用者覺得產品好不好用 | W06 |
| 可點擊原型 | Clickable prototype | 能點、能走流程，但背後沒有真的功能的試作品 | **它的目的是淘汰想法，不是做出產品** | W01（實作於 W06） |
| A/B 測試 | A/B test | 把使用者隨機分兩組，各看一個版本，比較哪個效果好 | 看結果時要小心三種常見誤讀（W07 會教） | W07 |
| 離線指標 | Offline metric | 上線前，在測試資料上算出來的表現數字 | 它好不代表上線會好 | W07 |
| 線上指標 | Online metric | 產品上線後，真實使用者行為算出來的數字 | 這才是真的，但會受很多外部因素干擾 | W07 |
| 幻覺率 | Hallucination rate | 產出內容中出現不正確資訊的比例 | AI 產品專屬的品質指標之一 | W07 |
| 拒答率 | Refusal / deflection rate | 系統選擇「我不知道」而不硬答的比例 | 太低代表它在亂答，太高代表它沒用 | W07 |
| 人工接手率 | Escalation rate | 需要轉給真人處理的比例 | 它同時是品質指標和成本指標 | W07 |
| 技術債 | Technical debt | 為了求快而留下的、以後要還的工程問題 | AI 系統還多一種「模型債」：沒人記得當初為什麼這樣調 | W08 |
| 單位經濟學 | Unit economics | 每做一單生意賺多少、賠多少 | **AI 產品每次呼叫的邊際成本不是零**，這是跟傳統軟體最大的差別 | W11 |
| 成效制定價 | Outcome-based pricing | 按客戶實際得到的成效收費，不是按使用量 | 聽起來誘人，但「成效」要能算得清楚才做得起來 | W11 |
| 投資報酬率 | ROI, Return on Investment | 投入多少、回收多少 | 誠實版本要包含失敗成本與機會成本 | W11 |

## 三、專案管理 vs 產品管理 vs AI 專案：三欄語彙對照

> 這份對照是給**專案管理背景**的學員的橋樑（對應 P0-1 修正）。左欄是你熟悉的詞，中欄是本課程會用的詞，右欄是在 AI 專案裡它又多了什麼。

| 你熟悉的（專案管理） | 本課程會用的（產品管理） | 在 AI 專案裡多了什麼 |
|---|---|---|
| **專案章程**：說清楚這個專案要幹嘛、誰批准 | **產品需求文件（PRD）**：說清楚要做什麼、為誰做、做到什麼程度算完成 | 多一段「資料從哪來、品質如何、誰維護」——**沒有這段的 PRD 在 AI 專案裡是不完整的** |
| **工作分解結構（WBS）**：把專案拆成可執行的工作包 | **使用者故事 + 功能拆解**：從使用者的角度拆，不是從工作量的角度拆 | 多一層拆解：每個步驟要標出是規則式、判別式、生成式，還是只能人做 |
| **里程碑**：時間點上的交付 | **產品階段**：探索 → 驗證 → 上線 → 成長 | AI 專案的第一個里程碑常常是「**資料盤點完成**」，不是「開發完成」 |
| **驗收標準**：功能做出來了沒（二元） | **驗收條件**：做到什麼程度算完成 | 從二元變成一個光譜：要定義「多好算夠好」，還要定義「誰來評」 |
| **需求變更控制**：變更要走流程、評估影響 | **優先級排序**：持續重排，變更是常態不是例外 | AI 專案的變更常常來自「資料不如預期」，而不是客戶改需求 |
| **風險登錄簿**：列出風險、機率、影響、對策 | **風險與治理設計**：偏誤、隱私、幻覺、濫用四大類 | 多一類專屬風險：**模型會過期**。要排定期重新檢視的責任人 |
| **關鍵路徑**：決定總工期的那條鏈 | **瓶頸**：決定產品能不能成立的那一步 | AI 專案的關鍵路徑常常落在**資料取得與清理**，不是開發 |
| **結案報告**：專案做完了，交付、歸檔 | **上線不是終點**：上線後才開始看真實指標 | AI 產品上線是**維運的起點**：效果會衰退，要有人負責發現 |

**一句話總結**：專案管理問「做完了沒」，產品管理問「做對了沒」，AI 專案還要再問一句「**它現在還對嗎**」。

## 四、本表的維護規則

| 時機 | 動作 |
|---|---|
| 每週教材開發時 | 把該週「本週新名詞」的內容合併進本表，填上首次出現週次 |
| 名詞定義修改時 | **先改本表，再改教材**，避免兩邊不一致 |
| 每學期 | 檢查「它代表什麼決策」欄是否仍成立；AI 相關條目特別注意 |

**本表不收錄**：特定廠商的功能名稱、模型版本號、價格——那些屬於 `AI工具與Agent教學規範.md` 附錄 A（易過期區塊）。
