# AI PM 經理人班 — 課程邊界與驗證規範

**適用範圍**：本課程 W01–W12 的所有教材、作業、案例與評量
**版本**：v1.0（2026-09-18）
**性質**：開發守則。每一週教材在動筆前、成稿後都要回到這份文件核對。

---

## 零、這份文件要解決的問題

課程內容最常見的失敗不是「寫得不好」，是**寫得太多、太深、太雜**。一份沒有邊界的 AI PM 教材會自然地往三個方向膨脹：

- 往技術方向膨脹 → 變成一堂講不清楚的 AI 概論
- 往產品管理方向膨脹 → 變成一張塞滿框架的 PM 百科
- 往工具方向膨脹 → 變成一份三個月就過期的操作手冊

所以這門課先定義**不教什麼**，再定義教什麼。

## 一、三條課程邊界

### 邊界 A · 對象邊界：給新手小白

**定義**：學員是完全沒有 AI 技術背景、也可能沒有正式 PM 訓練的在職工作者。他們的共同起點是「工作上開始被要求跟 AI 有關的事」。

| 界內（可以出現） | 界外（不得出現） |
|---|---|
| 用日常語言與比喻解釋概念 | 數學式、模型架構圖、論文引用 |
| 自然語言寫的提示範例 | 需要學員讀懂或修改的程式碼 |
| 現成的線上工具（瀏覽器可用） | 要求安裝開發環境、跑終端機指令 |
| 「這個詞在會議上代表什麼決策」 | 「這個詞的技術原理是什麼」 |
| 每週新名詞先定義再使用 | 未定義就直接使用的 PM／AI 術語 |

**硬性規則**

1. 每份教材出現的**專有名詞，第一次使用時必須有一句話的白話定義**（含 PM 術語，如 PRD、persona、驗收條件）。
2. 教材中不得出現學員需要理解的程式碼區塊。示範一律以自然語言提示呈現。
3. 每週學習總時數（閱讀 + 課堂 + 作業）**上限 5 小時**，超過就要砍內容，不是叫學員加油。

### 邊界 B · 工具邊界：學習「使用」AI 工具

**定義**：教會學員把 AI 當成一個能力很強但需要被指揮的協作者，並且有能力判斷它的產出可不可信。

| 界內 | 界外 |
|---|---|
| 提示的寫法、迭代、範本化 | 模型訓練、微調的實作 |
| 判斷 AI 產出對不對、可不可用 | API 串接、部署、MLOps |
| 工具的選型判斷準則 | 特定廠牌的介面操作步驟教學 |
| 把 AI 接進既有工作流程的方法 | 自建 AI 系統的架構設計 |
| 資料丟進工具前的風險判斷 | 資安技術方案（加密、權限系統設計） |

**硬性規則**

1. **廠牌中立**。教材不綁定特定工具，一律寫「任一主流對話式 AI 工具」。需要示範時，示範的是**提示本身**，不是某個產品的按鈕位置。
2. 不寫死任何廠商的價格、模型版本號、功能清單——這類內容集中放在可單獨更新的附錄，並標註「易過期」。
3. 凡涉及「公司資料能不能丟進 AI 工具」，一律導向**「先問你們公司的規定」**，不提供繞過內部政策的做法。

### 邊界 C · 職能邊界：學習專案經理（PM）

**定義**：教的是「在 AI 情境下做判斷、提問、溝通、論證」的能力，不是一套完整的產品管理學程。

| 界內 | 界外 |
|---|---|
| 問題定義、可行性判斷、取捨 | 敏捷／Scrum 認證考照內容 |
| 需求文件與驗收條件的寫法 | 專案管理軟體的操作教學 |
| 跨職能溝通與向上報告 | 組織設計、人資考核制度 |
| 指標設計與 ROI 論證 | 財務會計、統計學課程 |
| AI 產品的風險辨識與人在迴路設計 | 法律意見、法遵稽核程序 |

**硬性規則**

1. 涉及法規的內容只講**「這會如何影響你的產品設計決策」**，並明確標註：本課程不提供法律意見，實際適用請諮詢法務。
2. 所有 PM 框架只教「這門課後面會用到的那一部分」。不教完整版框架當作知識展示。
3. 每個 PM 概念都要能對應到一個**學員下週就用得上的動作**（一句話、一份文件、一個提問）。

## 二、灰區判定：三個問題

內容該留該刪拿不定主意時，依序問：

1. **不知道這件事，學員會不會做出錯的決策？**
   會 → 教。不會 → 移到延伸閱讀或刪除。
2. **學完之後，他能不能在下一次會議或下一份文件裡直接用上？**
   不能 → 刪。這門課不收藏知識。
3. **這個內容 12 個月後還成立嗎？**
   不成立 → 可以寫，但要標註「易過期」並集中放在可單獨更新的區塊。

三問都過不了的內容，不管寫得多好，都不進教材。

## 三、每週教材的固定結構與必備欄位

沿用 W01 已驗證的六段結構，並補上三個因應邊界的固定欄位：

| 段落 | 說明 | 必備欄位 |
|---|---|---|
| 1. 本週新名詞 | **新增**。當週會用到的 AI／PM 術語，各一句白話定義 | 不超過 8 個 |
| 2. 核心概念 | 3–4 個，每個都要有「所以你該做什麼」 | 每個概念附一則「給主管的提醒」 |
| 3. 產業案例 | 3 個，**至少 1 個是企業內部流程場景**（非 B2C 科技產品） | 標註案例查證日期 |
| 4. 自我檢驗 | 6 題，**前 2 題為判斷／選擇題**，後 4 題申論 | 附參考方向 |
| 5. 實踐作業 | 1–2 份，**必須標示完成時間估計** | 附「非 PM 背景替代版」 |
| 6. 延伸思考 + 推薦閱讀 | 開放題與資源 | 易過期資源另立區塊 |

## 四、五類驗證者與各自的檢核表

課程內容在成稿後，必須經過下列五類專業人士測試與驗證。**每一類負責守住不同的一條線**。

### 驗證者 1 · 現職產品經理

**他守的線**：專業正確性。內容不能為了簡化而說錯。

| # | 檢核項目 | 判定 |
|---|---|---|
| 1.1 | 課程對 AI 產品實務的描述，是否與你的真實工作經驗相符？ | 1–5 |
| 1.2 | 有沒有為了好懂而簡化到**已經失真**的說法？ | 列出 |
| 1.3 | 案例的細節與結論是否經得起檢驗？有沒有過時或誤植？ | 列出 |
| 1.4 | 作業的產出，拿到真實團隊裡是否站得住腳？ | 1–5 |
| 1.5 | 有沒有明顯該講卻沒講的實務重點？ | 列出 |
| 1.6 | 對已有 PM 經驗的學員，本週是否有可跳過／可加深的路徑？ | 是／否 |

### 驗證者 2 · 具備專案管理經驗人士

**他守的線**：可執行性。方法要能真的跑起來，不是紙上框架。

| # | 檢核項目 | 判定 |
|---|---|---|
| 2.1 | 本週的方法／檢核表，是否能直接套進一個真實專案？ | 1–5 |
| 2.2 | 時程、資源、風險的處理方式是否務實？ | 1–5 |
| 2.3 | 課程用的產品管理語彙，對專案管理背景的人是否有對照解釋？ | 是／否 |
| 2.4 | 作業的時間估計是否合理？（請實際估一次） | 列出落差 |
| 2.5 | 有沒有「聽起來很好但實際上沒人做得到」的步驟？ | 列出 |
| 2.6 | 交付物的定義是否清楚到可以驗收？ | 1–5 |

### 驗證者 3 · 部門主管與團隊領導者

**他守的線**：決策價值。內容要幫得上「要不要投、怎麼帶團隊」的判斷。

| # | 檢核項目 | 判定 |
|---|---|---|
| 3.1 | 本週內容能否幫你做出一個具體的管理決策？是哪一個？ | 列出 |
| 3.2 | 「給主管的提醒」是否切中你真正的痛點？ | 1–5 |
| 3.3 | 你會不會願意讓下屬花 5 小時上這一週？為什麼？ | 是／否 + 理由 |
| 3.4 | 內容是否幫你問出更好的問題，而不只是給你答案？ | 1–5 |
| 3.5 | 有沒有對管理現實太過理想化的假設？ | 列出 |
| 3.6 | 學完之後，團隊層級的產出是什麼？（一份文件／一個規範／一場會議） | 列出 |

### 驗證者 4 · 數位轉型推動者

**他守的線**：落地路徑。從「知道」到「組織真的改變」之間的那一段。

| # | 檢核項目 | 判定 |
|---|---|---|
| 4.1 | 內容是否處理了「既有流程盤點 → 選切入點」這個真實起點？ | 是／否 |
| 4.2 | 面對組織阻力、跨部門協調，課程給的方法是否夠用？ | 1–5 |
| 4.3 | 是否有可衡量的導入前後對照方式？ | 是／否 |
| 4.4 | 內容是否只適用於科技業？傳統產業套得上嗎？ | 1–5 |
| 4.5 | 有沒有淪為「為了用 AI 而用 AI」的內容？ | 列出 |
| 4.6 | 學員能否把本週內容轉成一份可以對上報告的材料？ | 是／否 |

### 驗證者 5 · 非產品經理背景的職場人 ★ 關鍵驗證者

**他守的線**：可理解性。**這一類是課程的警示鳥——他看不懂的地方，就是課程失效的地方。**

| # | 檢核項目 | 判定 |
|---|---|---|
| 5.1 | 讀完後有沒有哪一段你完全不知道在講什麼？（請標出**行號或段落**） | 列出 |
| 5.2 | 有沒有沒解釋就直接用的專有名詞？ | 列出 |
| 5.3 | 作業你有沒有辦法獨力完成？卡在哪一步？ | 列出 |
| 5.4 | 讀完後你能不能用自己的話向同事解釋本週重點？ | 是／否 |
| 5.5 | 實際花了多少時間？ | 分鐘 |
| 5.6 | 有沒有讓你覺得「這門課不是為我開的」的瞬間？ | 列出 |

## 五、驗證流程

### 三道關卡

| 關卡 | 時機 | 執行者 | 動作 |
|---|---|---|---|
| **關卡一 · 邊界自檢** | 教材成稿前 | 教材作者 | 用第一、二節的邊界表與三問逐條核對，填「邊界自檢表」 |
| **關卡二 · 交叉驗證** | 教材成稿後 | 五類驗證者中**至少 3 位** | 填各自檢核表，**其中必須包含「非產品經理背景的職場人」1 位** |
| **關卡三 · 試教回饋** | 首次授課後 | 實際學員 | 收集作業完成率、卡點位置、實際耗時 |

### 通過門檻

- 所有 1–5 分項目的**平均 ≥ 4.0**
- 驗證者 5（非 PM 背景）的**可理解性題項 ≥ 3.5**
- **無任何 P0 問題未處理**

### 問題分級

| 等級 | 定義 | 處理 |
|---|---|---|
| **P0** | 內容錯誤、越出三條邊界、非 PM 背景者完全看不懂 | 修正後才能發布 |
| **P1** | 可理解但影響學習效果（時數超標、案例不貼切、缺少替代作業） | 本版修正 |
| **P2** | 改善建議、加分項 | 下一版處理 |

### 回饋紀錄格式

每次驗證產出一份 `WNN-驗證回饋-<角色>.md`：

```
週次：W03
驗證者角色：非產品經理背景的職場人
驗證日期：YYYY-MM-DD
實際耗時：___ 分鐘

【分項評分】1.1 ___ / 1.2 ___ ...
【P0 問題】
【P1 問題】
【P2 建議】
【一句話總評】
```

## 六、每週開發前的最後檢查（10 題快篩）

動筆前、送審前各跑一次。**任何一題答「否」就回去改。**

1. 這一週的內容，零技術背景的人讀得懂嗎？
2. 有沒有出現學員需要讀懂的程式碼？（應為「沒有」）
3. 專有名詞都在第一次出現時定義了嗎？
4. 教的是「用 AI」還是不小心教到「做 AI」？
5. 工具內容是否維持廠牌中立、不會半年後失效？
6. 每個 PM 概念都對應到一個學員下週用得上的動作嗎？
7. 至少有一個案例是企業內部流程場景嗎？
8. 總時數估計在 5 小時以內嗎？
9. 作業有沒有「非 PM 背景替代版」？
10. 有沒有給主管／給團隊層級的提醒？

## 七、明確的禁區清單

以下內容一律不進教材，無論學員要求或內容看起來多有價值：

- 法律意見、合規判定、個資法適用性的結論
- 繞過公司資安或採購政策的做法
- 未經查證的市場數字、成長率、市占率
- 特定廠商的即時價格與模型版本清單（改放可單獨更新的附錄）
- 需要寫程式、架環境、串 API 才能完成的作業
- 承諾式的職涯說法（如「學完就能轉職 AI PM」）
- 超過 12 個月未重新查證的案例
